## 2. 当前核心结论

本模块不识别“喝水”或“吞药”这种无法从当前相机构图中稳定观察的医学动作，而是判断两个可观察的桌面完成事件：

```text
桌面上同时稳定看到橙杯和蓝杯
  -> 橙色药杯稳定离开桌面 = medicine_completed
  -> 蓝色水杯稳定离开桌面 = water_completed
  -> success
```

可以用一句话概括：

> 先确认两只杯子在桌上，之后橙杯从桌面区域消失视为服药完成，再看到蓝杯从桌面区域消失视为服水完成。

这里的“离开桌面”指杯子不再存在于桌面 ROI，不要求它完全离开整幅画面。

### 成功与失败

| 终态 | 含义 | launcher 结果 |
| --- | --- | --- |
| `success` | 已按顺序观察到 `baseline_ready -> medicine_completed -> water_completed -> success` | 退出码 0，播报完成提示 |
| `timeout` | 60 秒内没有形成完整 success，包含只完成药杯、只移动水杯或一直未建立完整流程 | 退出码非 0，播报“本次服药未完成。” |
| `session_failed` | 相机、帧、模型或视觉事件流发生技术错误 | 退出码非 0，播报“本次服药未完成。” |
| `Ctrl+C` | 操作员主动中止本场演示 | 退出码 130，清理本场子进程 |

失败不只有超时一种。业务动作未在 60 秒内完成会进入 `timeout`；相机、模型或事件异常会进入 `session_failed`。蓝杯先离桌只产生 `sequence_warning`，不会立即失败，系统仍会继续等待正确顺序。

## 3. 明确不使用的判断信号

当前模型不结合手部来判断，也不寻找以下证据：

- 手部检测框、手部关键点或手部 mask；
- 手与杯子是否接触；
- 手杯距离、抓取姿态或拿起轨迹；
- 杯子是否靠近嘴部；
- 杯子倾斜角度、嘴边停留时间或吞咽动作；
- 杯子是否在离桌后重新放回。

因此，当前逻辑是“杯子桌面存在性 + 确定性时序”，不是“杯子 + 手部联合动作识别”。

## 4. 为什么采用这个简化方案

当前比赛环境具有明确先验：构图固定、桌子固定、杯子颜色固定，药杯为橙色，水杯为蓝色。在这种受限场景中，最高信息量的事实不是手的细节动作，而是杯子是否仍在桌面上。

旧路线尝试过嘴部、杯体倾斜、停留、手杯接触和完整拿放动作，但这些信号在 G1 前视 RGB 的当前构图中并不稳定：

- 嘴部可能不在画面中；
- 手部容易遮挡杯子；
- 接触和小幅滑动很难从单视角稳定区分；
- 杯子离桌后是否放回与“本次拿起已完成”无关；
- 增加手部或姿态模型会增加依赖、误差和部署成本，但不会改变当前可观察任务的实质。

所以本模块选择“最小可观察事实”，并把连续性、顺序、去重和超时交给状态机处理。

## 5. 视觉模块完整架构流程（后续接回 VLA 时）

下列是视觉模块与后续 VLA、语音和数据库接回后的完整架构边界。当前 2026-08-08 演示版只运行第 2.1 节的一键官方 ASR + TTS + 视觉流程，不加载 VLA 或 SQLite。

```text
VLA 完成蓝色水杯递交
  -> VLA 释放模型和运行资源
  -> 启动视觉 worker 与有界新帧缓存
  -> 视觉接帧与“请服药”语音并行开始
  -> 橙杯/蓝杯颜色候选提取
  -> 桌面 presence 单帧分类
  -> 确定性状态机归约
  -> baseline / warning / medicine / water / success 事件
  -> 追加写入视觉事件和 SQLite 会话投影
  -> 按顺序完成后更新服药任务
```

视觉、VLA、语音和数据库保持独立 owner：

- VLA 只负责递交，不得直接把“已递交”写成“已服药”；
- 视觉感知只产生逐帧杯子状态，不直接产生 success；
- 状态机唯一拥有基线、顺序、去重和成功逻辑；
- 语音只播放提示或顺序警告，不判断视觉成功；
- SQLite 保存同一会话的事件序列，并在顺序完整时投影任务完成。

### 6.1 输入

- G1 头部前视 RGB；
- 解码尺寸：`480 x 640 x 3`；
- 像素格式：`bgr24`；

- 蓝色水杯 `water_blue`；

### 6.2 感知层单帧输出

每只杯子只输出以下四态之一：

| 状态 | 含义 | 是否可推进完成 |
| --- | --- | --- |
| `on_table` | 杯子在桌面 ROI 内 | 只能用于建立或恢复基线 |
| `off_table_visible` | 杯子仍在整幅图中可见，但已明确离开桌面 | 连续稳定后可快速确认 |
| `not_visible` | 没有在当前场景找到有效杯体 | 需要更长连续窗口才能确认 |
| `uncertain` | 遮挡、颜色候选无效或证据不足 | 不推进任何完成事件 |

### 6.3 事件输出

当前事件集合为：

```text

sequence_warning
medicine_completed
water_completed
success
timeout
session_failed
```

事件保存 source frame 范围、单调时间、杯子类型、置信度和模型 ID，用于回放和追溯。

## 7. 当前使用的模型

### 7.1 模型组成

当前不是大型深度学习模型，而是适合固定比赛场景的轻量组合：

1. HSV 颜色分割：独立提取橙色药杯和蓝色水杯候选。
2. 固定 scene ROI 与 table ROI：排除无关画面和桌外同色背景。
3. 形态学处理：当前 kernel size 为 5，用于收敛颜色 mask 中的碎片。
4. 连通域候选：按最小面积、宽高、位置和杯底坐标筛选杯体。
5. 每杯独立 1-nearest-neighbor（1-NN）：使用人工复核帧的特征，对 `on_table/off_table` 做轻量监督分类。
6. 确定性时序 reducer：完成稳定基线、离桌确认、顺序、warning 去重和 success 派生。

模型 ID：

```text
g1_tabletop_cup_presence_hsv_knn_v3
```

模型目录：

```text
/home/user/github-product/g1-dex3-care-vla/data/visual/elder-medication-tabletop-v2/models/tabletop-presence-hsv-knn-v3-20260807
```

### 7.2 1-NN 特征

每只杯子的当前特征只来自 HSV 候选和 ROI 几何，包括：

- 是否找到有效杯体；
- 规则层初步判断是否在桌；
- 桌面 ROI 内连通域的 bbox、面积、中心和杯底位置；
- 整个 scene ROI 内连通域的 bbox、面积、中心和杯底位置。

模型不输入手部像素、手部检测、人体姿态或面部特征。

### 7.3 模型规模与速度

- `model.json` 约 5 MB；
- 当前开发机单帧推理约 2.14 ms；
- 输入为 640 x 480 BGR 帧；
- 不依赖 PyTorch、手部检测器或人体姿态模型；
- 适合在 G1 机载或随机器人运行的本地计算侧离线运行。

### 7.4 逐帧推理细节

模型对每一帧执行同一条固定流水线；橙杯与蓝杯分别处理、分别分类，彼此不共享颜色候选。

```text
640×480 BGR 帧
  -> BGR 转 HSV
  -> 各杯 HSV 阈值分割
  -> 5×5 椭圆核开运算，去除小碎片
  -> 在 scene ROI 和 table ROI 中筛选最大合格连通域
  -> 生成 18 维几何/可见性特征
  -> 各杯独立标准化 1-NN，判定 on_table / off_table
  -> 映射为四态 presence
  -> 交给状态机做连续确认与顺序判定
```

这里的“最大合格连通域”不是简单取所有同色像素：候选必须同时满足训练时得到的最小面积、最小/最大宽度和最小/最大高度。这样可滤掉桌面反光、衣物小色块和零碎噪声。`scene ROI` 用于判断杯子是否仍在画面中，`table ROI` 只用于判断其是否仍在桌面区域。

当前冻结 artifact 的 HSV、ROI 和几何筛选参数如下。坐标格式为 `[x0, y0, x1, y1]`，原点在图像左上角。

| 杯子   | HSV 下界 / 上界                    | table ROI          | scene ROI        | 桌面锚点 y | 面积下限 | 宽度范围 px | 高度范围 px |
| ---- | ------------------------------ | ------------------ | ---------------- | -----: | ---: | ------- | ------- |
| 橙色药杯 | `[5,110,99]` / `[18,255,255]`  | `[40,140,620,470]` | `[40,0,620,470]` |    210 |  462 | 17–143  | 24–220  |
| 蓝色水杯 | `[88,80,73]` / `[112,255,255]` | `[80,140,500,460]` | `[80,0,500,460]` |    210 |  382 | 19–157  | 20–186  |

规则层先给出一个可解释的初判：table ROI 中存在合格候选，且候选框底边的 y 值不小于对应的桌面锚点，即为 `on_table`；若 scene ROI 中仍有候选、其顶部高于 table ROI 上沿至少 10 px，且候选底边的 y 值小于桌面锚点，则为 `off_table_visible`；scene ROI 中没有合格候选为 `not_visible`；其余相互矛盾或证据不足的情况为 `uncertain`。v3 会以 1-NN 的结果校正上述 `on_table/off_table` 初判，但不会跳过这套候选提取和输入校验。

### 7.5 监督分类层（HSV + 1-NN）

v3 的监督部分是每只杯子各一套 `k=1` 最近邻分类器，不是神经网络，也没有可训练卷积层。它保留经过人工确认的帧特征；新帧在标准化特征空间中寻找距离最小的历史样本，并继承该样本的 `on_table` 或 `off_table` 标签。

每个样本是 18 维特征：

- 可见标记、规则层 `on_table` 标记、table/scene 连通域面积的 `log1p` 值；
- table 连通域是否存在、bbox 的归一化 `x/y/宽/高`、归一化面积和 bbox 底边；
- scene 连通域的同一组 7 个特征。

训练前会按杯子分别计算每一维的均值与标准差，把样本转换为 `(x - mean) / std`；极小标准差按 1 处理，随后以平方欧氏距离取唯一最近邻。`uncertain` 人工标注不会参与拟合，以免把“不知道”伪造成正例或反例；`off_table_visible` 和 `not_visible` 都作为 `off_table=0`，`on_table` 作为 `on_table=1`。

| 分类器 | 样本数 | 在桌正例 | 离桌/不可见反例 | 拟合范围 |
| --- | ---: | ---: | ---: | --- |
| `medicine_orange` | 7,305 | 6,289 | 1,016 | 全部 12 条人工复核会话 |
| `water_blue` | 7,295 | 6,141 | 1,154 | 全部 12 条人工复核会话 |

HSV 基础参数先从原固定划分中的 001–008 训练会话校准：每条取 30 帧，在预设种子 ROI 中收集粗 HSV 范围内的像素，取每通道 1%/99% 分位数，再扩展 `[4,30,30]` 的 HSV 边界；几何面积和宽高范围则由校准帧中杯体连通域的中位数导出。之后 1-NN 按人工确认的语义使用全部 12 条会话拟合。因此当前模型大小约 5 MB 的主要原因是保存了全部最近邻样本，而非保存大型网络权重。

模型输出中的 `confidence` 是 HSV 规则层基于候选面积生成的启发式证据值，不是 1-NN 的概率、也不表示“已服药”的概率。状态机不依据这一数值直接完成任务：只有四态在规定帧数内连续成立，才可能产生业务事件。

### 7.6 模型适用范围与升级条件

该模型只适用于当前固定相机、固定桌面、固定橙/蓝杯和已校准光照范围。它不能识别吞咽、饮水、手杯接触，也不能证明在未见过的背景、杯型、相机角度或强烈光照变化中具有泛化能力。

artifact 中的 `production_qualified=false` 只表示离线拟合本身不能自动成为生产资格；当前文档记录的真实 G1 ZMQ 60 秒演示才是该固定场景的 `demo_qualified` 证据。只有真实流中出现可复现的误报或漏报、且最小补采与人工复核仍无法解决时，才考虑替换为轻量杯体检测或分割模型；不因“模型看起来不够大”而引入手部、姿态或云端模型。

## 8. 确定性状态机

```text
WAIT_TABLE_BASELINE
  两杯连续稳定在桌 -> baseline_ready -> WAIT_MEDICINE
  基线前的任何移动/缺失 -> 静默忽略

WAIT_MEDICINE
  橙杯稳定离桌 -> medicine_completed -> WAIT_WATER
  蓝杯先稳定离桌 -> sequence_warning，但不失败

WAIT_WATER
  蓝杯稳定离桌 -> water_completed -> success

ANY NONTERMINAL STATE
  短时遮挡/低置信/不确定 -> 继续等待
  达到会话上界 -> timeout
  输入或资源失效 -> session_failed
```

### 8.1 基线为什么必须存在

VLA 的最后一个动作是将蓝色水杯递给老人。视觉会话刚开始时，蓝杯可能还在交接过程中。如果没有基线，系统可能把这次交接误认为服水。

因此，必须先连续看到两只杯子同时稳定在桌面，才允许后续离桌事件进入任务逻辑。

### 8.2 时序参数

当前固定数据的默认参数为：

- 双杯基线窗口：1 秒；
- 基线期间双杯质心最大漂移：15 px；
- 如果首帧尚未同时看到双杯，首次回桌基线增加约 `1/6` 窗口（30 FPS 时为 5 帧）；
- 明确可见离桌快速确认：0.2 秒；
- 完全不可见慢确认：1.5 秒；
- 当前比赛演示会话上界：60 秒；
- 部署时按实际采样 FPS 换算帧数。

单帧丢失、短时遮挡、`uncertain` 和桌面内滑动都不得直接完成事件。

### 8.3 蓝杯先离桌的处理

建立基线后，如果橙杯还没有完成，蓝杯先达到稳定离桌门槛，系统产生一次：

```text
sequence_warning
```

对应语音：

> 请先把蓝色水杯放回桌面，再拿橙色药杯。

## 11. 人工复核需要做什么

人工复核不需要判断手势，也不需要直接填写 success。最小复核内容为：

1. 检查会话与原始帧是否一致，图片是否完整。
2. 确认固定桌面 ROI 能覆盖比赛中两只杯子的正常放置区域。
3. 分别为橙杯和蓝杯标出从第 0 帧到最后一帧连续覆盖的四态区间：`on_table|off_table_visible|not_visible|uncertain`。
4. 对遮挡、运动模糊或颜色候选无效帧，使用 `uncertain`，不猜测杯子坐标。
5. 复核特殊会话的事实语义，例如 009 的“离桌后无需放回”和 011 的“滑动但未离桌”。
6. 由标注工具校验区间连续性、冻结 source/review SHA-256，再调用 reducer 派生事件和 session success。

人工只负责“每只杯子在每个时间段是否还在桌面”这个事实。完成顺序、warning 和 success 必须由状态机统一派生，避免人工复核者各自理解业务逻辑。

# 陕西省养老招呼大赛项目总览

> 更新：2026-08-12  
> 项目：G1 EDU+ CN / 23DoF 养老服药辅助演示  
> 用途：赛前确认当前可演示能力、现场启动入口、数据来源和安全边界。

## 1. 当前结论

项目已有三条独立、可替换的能力链：语音、视觉和 G1 上肢/VLA。比赛演示以现场可观察、可停止、可重复为第一目标；离线回放、训练样本和模型指标只服务于下一次实机演示。

当前已完成的固定场景演示是 PC2 上的“语音 + 桌面视觉”服药流程：先稳定看到橙色药杯和蓝色水杯都在桌面；橙杯稳定离开桌面记为服药完成；随后蓝杯稳定离开桌面记为服水完成；二者顺序正确时成功。它不声称识别吞咽或真实医疗结果。

G1 XR 遥操、原生录制、EpisodeV2 导出和训练 release 已连通。VLA 的部署原则不变：候选 checkpoint、推理和相机输入最终必须运行在 G1 本机侧或随机器人运行的一侧；训练服务器、SSH tunnel 和远端 HTTP 不能作为比赛部署方案。

## 3. 比赛演示入口

当前已通过实机验收的轻量演示运行在 PC2：

```bash
/home/unitree/medication_robot/start_robot.sh
```

它会单实例运行以下流程：检查或启动 `teleimager`，后台启动官方 ASR 记录文本，启动官方 TTS 与 60 秒有界视觉会话。

```text
session_started
  -> baseline_ready（橙杯、蓝杯同时稳定在桌）
  -> medicine_completed（橙杯稳定离开桌面）
  -> water_completed（蓝杯稳定离开桌面）
  -> success
```

蓝杯先离桌只播报顺序提醒，不立即失败；会话上界 60 秒，超时、相机/模型错误或人工 `Ctrl+C` 都不会被误报为成功。运行后优先查看：

```bash
tail -F /home/unitree/g1_competition_demo_logs/latest/visual.jsonl
cat /home/unitree/g1_competition_demo_logs/latest/launcher_summary.json
```

语音在当前演示中是交互和播报层，不拥有成功判定。ASR 当前使用 CPU 版本，官方 JetPack 5.1.1 的 Python 3.8 GPU wheel 与现有 Qwen ASR 的 Python 要求不兼容；这不是当前固定场景演示的阻断项。

## 4. 视觉模块

视觉只读 G1 前视 RGB，不发布 DDS、不控制机器人。固定场景内使用 HSV 颜色候选、固定 ROI 和轻量 1-NN，输出每个杯子的四态：`on_table`、`off_table_visible`、`not_visible`、`uncertain`；确定性状态机才拥有基线、顺序、去重、超时和 `success`。

当前 artifact 是 `g1_tabletop_cup_presence_hsv_knn_v3`。12 条人工复核会话的全量拟合回放结果为 6 TP、6 TN、0 FP、0 FN；这证明当前固定场景回放和实机演示通过，不等同于独立泛化评测。出现新的可复现误报或漏报时，再针对该问题最小补采，不能为了形式扩大数据集。

原始画面可能包含人脸，不能提交 Git 或公开上传。视觉只表示“可观察的杯子顺序动作已完成”，不表示吞咽、药物剂量或医疗效果已确认。

## 5. XR 遥操与采集

实时遥操唯一 owner 是官方 `teleop_hand_and_arm.py`；项目侧只记录事实、做安全回归和训练导出，不重写控制器。正式连续采集使用官方 Motion Mode 和 `official_continuous_ik_v1`：`r` 进入分段控制，`s` 开始/保存一段，`a` 成功、`f` 失败、`o` 碰倒物体，`q` 正常退出。

V3 连续遥操是经过批准的无 deadman 例外：手势停止、事件过期或退出 Quest 页面都不能当作自动停止；现场必须有人监护，机器人需在吊装/限位范围内，发现异常应在终端按 `q` 并按现场恢复流程处理。单段上界为 180 秒。

采集前先在 PC2 保持 `teleimager-server`，再在控制主机执行冻结的只读 preflight；图像服务未 ready、控制主机无法访问 `.164:55555`、或者机器人模式不匹配时，不启动遥操。正式操作会改变实机状态，必须逐次获得明确确认。

## 6. 训练数据：从原始录制到 release

官方 native `data.json` 和 JPEG 是不可变 source，不是训练合同。它们保存任务文字、帧号、原生关节快照和图像路径，但不能单独证明最终发给 arm/Dex3 的 24D 命令，也不能把动作、写入结果、后观测和 RGB 可靠地关联起来。

```text
native data.json + JPEG
        +
XR trace（raw input、writer fact、after observation、人工结果）
        -> 验证 source 与帧/哈希/时间/维度
        -> EpisodeV2
           raw_input -> mapped_action -> sent_action
                     -> observation -> execution_result -> rgb_reference
        -> immutable release manifest
```

EpisodeV2 固定 `upper_body_24d_v1` 布局：双臂 10D、左 Dex3 7D、右 Dex3 7D。`mapped_action` 是遥操映射目标；训练监督标签是三路 writer 均成功后形成的最终 `sent_action`。每个标签还必须具备对应的 writer 结果、后观测、RGB 引用、对齐误差和 SHA256，因此训练器不得直接扫描 `data.json` 或整个 episode 目录。

## 7. 三模块边界

| 模块 | 唯一职责 | 不应做的事 |
| --- | --- | --- |
| 语音 | 接收/记录语音，播报状态和提示 | 不根据文本宣称服药成功 |
| VLA | 输出受校验的 24D 候选动作 | 不直写 DDS，不自己判定任务完成 |
| 视觉 | 读取画面，输出结构化事件 | 不控制 G1，不把单帧结果直接当 success |
| runtime/官方 controller | 限位、执行、最终 sent command 和状态回读 | 不由训练/策略脚本绕过 |
| bridge | 编排三者的结构化交接 | 不吞掉模块失败，也不创造第二套 owner |

更换 VLA checkpoint 时，流程固定为：先以当前 reference 模型在同一场景实机记录基线，再只替换 checkpoint/模型服务并复验；只有对比证据表明数据不足时才补采或重训。没有这种实机比较，不改 action 后处理、启发式策略或 controller 语义。

## 8. 赛前检查与停止条件

赛前确认相机、网络、模式、吊装/限位、现场人员分工和日志目录；控制主机与 G1 的连接、DDS Domain/Topic 和 PC2 图像端口必须正常。任何机器人动作前，明确本次范围、时间上界、验收结果与停止方法。

立即停止并进入恢复流程的条件包括：异常响声、跳变、失控趋势、追踪/图像明显中断、未知模式切换、writer/RPC 异常或人员进入危险范围。不要用断开 Quest、停止手势或假定自动保持作为 V3 的停止手段。

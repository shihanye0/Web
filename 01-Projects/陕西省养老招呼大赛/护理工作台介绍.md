## 一、 系统定位与比赛价值

### 1. 为什么需要护理工作台？
在养老机构场景下，**宇树 G1 机器人不仅是一个物理执行端，更是机构照护体系中的前置触手**。单靠机器人现场语音或动作无法构成完整的医疗照护服务链条。
比赛正式业务定义了端到端照护闭环：
$$\text{G1 现场感知/交互} \longrightarrow \text{事件与诉求入库} \longrightarrow \text{护士工作台接单跟进} \longrightarrow \text{AI 总结与终生健康档案}$$

### 2. 核心职责边界
* **机器人 G1 侧（执行端）**：负责主动情绪波动检测（开心/悲伤/生气）、陪伴多轮对话、表达性肢体交互（挥手/鼓掌/掌心邀请）、跌倒/呼救检测等。
* **护理工作台 Care Console（管理中枢）**：面向养老院护士、管理人员及大赛评委，提供长辈档案管理、照护需求待办追踪、异常告警协同处置、多轮交流回看以及基于大模型的会话自动总结。

| 环境 | 访问地址 | 认证方式 | 数据状态 | 核心用途 |
| :--- | :--- | :--- | :--- | :--- |
| **云端公网控制台** | [https://82.157.186.52:8443/](https://82.157.186.52:8443/) | 页面登录，账号 `careadmin`，高强度 PBKDF2 密文 | **实时自动同步最新数据**（由本地后台 1~2 秒异步推送） | 远程评委展示、手机/iPad 查阅、多终端演示 |
| **本机本地控制台** | `http://127.0.0.1:8766` | 局域网/本机直接访问，免登 | **实时最新**（G1 每次互动后即时更新） | G1 实机运行调试、现场比赛演示、技术保障 |

### 1. 本机工作台启动
在工程根目录运行：
```bash
# 方式 1：前台运行（查看实时控制台日志）
python3 -m care_console --port 8766

# 方式 2：后台长期运行（关闭终端不退出）
nohup python3 -m care_console --port 8766 > care_console.log 2>&1 &
```
数据存储于本地 SQLite：`care_console/runtime/console.db`。

### 2. 云端服务器配置架构
* **服务器 IP**：`82.157.186.52`（腾讯云服务器）
* **接入层**：Nginx 独立监听 `8443` 端口，强制开启 TLS/HTTPS（Let's Encrypt IP 证书及自动续期），配置安全响应头（CSP、HSTS、SameSite Cookie）及防爆破限流（每分钟 5 次重试限制）。
* **应用层**：systemd 服务 `care-console.service`，监听 `127.0.0.1:8766`，配置 `EnvironmentFile=/etc/care-console/cloud.env`（加载 DashScope API Key 用于总结生成，以及同步 Token）。
* **数据持久层**：`/var/lib/care-console/console.db`、`/var/lib/care-console/interaction.db`。

## 三、 核心业务功能

日常导航包含**工作台、老人档案、情绪记录、异常记录、互动记录、系统维护**六大版块：

### 1. 机构与长辈档案管理 (Elder Profile)
* 统一维护长辈基础资料：姓名、年龄、性别、房间号（如首位正式长辈王大爷，男，76 岁，101 房），并支持长辈独立照护备注维护。
* 严格多长辈数据隔离：切换长辈时自动清除旧上下文与异步查询，避免跨长辈数据混淆。

### 2. 照护需求待办与处置跟踪 (Care Needs & Tasks)
* **需求自动捕获**：当长辈在陪伴对话中表达现实诉求（如悲伤后明确表达“口干/想喝水”，或长辈直接要求联系家人）时，系统自动生成结构化照护需求单（`elder_need`）。
* **紧急程度流转**：按 `urgent > high > normal` 排序，状态包括 `detected`（已捕获）→ `in_progress`（处理中/护士跟进）→ `completed`（已完成）。
* 护士可直接在工作台接单、记录处置日志并流转状态。

### 3. 情绪记录与视觉审计 (Emotion Records)
* **主动情绪检测**：记录 G1 视觉对长辈“开心 (happy)”、“悲伤 (sad)”、“生气 (angry)”的三类主动波动检测结果。
* **证据溯源**：区分主线面部识别（`stable_face`）与强动作补充线索（点赞、握拳下落、低头捂脸、双手鼓掌、单手挥手），保留视频帧时间轴与置信度，不伪造实时当前状态。

### 4. 异常安全监测 (Anomaly Monitoring)
* 对接跌倒检测与声音求救监测模块（L3 级别疑似跌倒、呼救关键词触发）。
* 提供护士闭环工作流：“异常推送 → 护士接单 → 现场确认/处置 → 归档或标记误报”。

### 5. 陪伴对话与大模型会话自动总结 (AI Summaries)
* **交流原文留存**：记录每轮长辈原话（ASR 转写）、机器人回复（LLM 生成）、意图判定（情绪分享/日常闲聊/讲故事/讲笑话等）及多轮打断记录。
* **AI 总结四要素**：单次会话结束后，后台独立任务异步调用通义千问模型，自动提炼四项核心结论：
  1. **起因**：本次交流触发的背景；
  2. **诉求（需求）**：严格依据同会话长辈原话提取，避免 AI 臆测动机；
  3. **过程**：G1 的安抚、陪伴、讲故事或打断处理细节；
  4. **结果**：情绪变化及本地结束语记录。

## 四、 边缘至云端自动同步机制 (Auto-Sync)

针对“现场实机互动实时映射至云端”的需求，系统采用了**高可靠、非阻塞的应用层增量异步推送架构**（`care_console/sync.py`）：

### 1. 架构拓扑
```text
[ G1 现场互动 ] 
       │ 写入本地磁盘 (100% 本地离线闭环，不依赖外部网络)
       ▼
[ 本地日志 / SQLite (console.db) ] 
       │ 
       ▼
[ 本地后台守护协程 (cloud_sync) ]
       │ 每 2 秒增量轮询未同步游标
       │ 异步安全网络推送 (带 X-Care-Sync-Token 令牌)
       │ 断网时仅记录 warning 游标不前移，网络恢复自动重试 (绝不卡顿机器人)
       ▼
[ 云端专用接口 (POST /api/sync/push) ]
       │ 机器令牌鉴权 (绕过前端 Cookie)
       │ 基于唯一键 (session_key, external_id, dedupe_key) 天然幂等入库
       ▼
[ 云端管理工作台 (82.157.186.52:8443) ]
       │
       ▼
[ 手机 / iPad / 远程评委浏览器 ] (1~2 秒内自动刷出最新记录)
```

### 2. 同步内容矩阵
* **情绪记录 (`events`)**：主动检测的 happy/sad/angry 及置信度、检测依据；
* **会话总览 (`companion_sessions`)**：会话起始时间、状态、初始/结束情绪、AI 四要素总结；
* **对话实录 (`companion_records`)**：长辈说的每句话、G1 回复的每句话、打断及控制回执；
* **视觉快照 (`emotion_observations`)**：高频面部与姿态分析快照；
* **照护需求 (`elder_need`)**：长辈对话中触发的具体照护诉求（如递水、联系家属）。

> **评委提问**：“你们机器人跟老人聊完天、测完情绪，护士在后台怎么看？是单机版还是联网的？”  
> **推荐回答**：  
> “报告评委，我们的系统遵循**‘边缘高可靠自治 + 云端集中管理’**的云边协同架构：  
> 1. **现场实机端**：G1 机器人在现场与老人交互时，所有情绪感知、语音多轮对话、动作控制及照护需求捕获都在本地边缘闭环运行，确保比赛与突发断网环境下 100% 稳定可靠；  
> 2. **机构管理端**：我们已经在云端部署了生产级护理工作台（可提供 HTTPS 公网访问）。机器人产生的长辈情绪波动、照护诉求和异常监测结果，会在后台生成结构化的‘护士待办任务’，并通过通义千问大模型自动提炼四要素会话总结，方便护士站远程跟进与长辈健康档案归档。”

# 离线漏斗与决策漏斗

## 核心结论

离线漏斗和决策漏斗解决的是两件不同的事，必须分开使用：

| 漏斗 | 要回答的问题 | 产出 |
| --- | --- | --- |
| 离线漏斗 | 这个 checkpoint 的问题在哪一层？ | 问题 owner 与可验证证据 |
| 决策漏斗 | 基于现有证据，下一步应该做什么？ | 训练、采集、改 pipeline、上机或停止的决策 |

不能因为某个离线指标改善，就直接得出“应继续训练”或“可以上机”的结论。

---

## 一、离线漏斗：定位 checkpoint 的问题 owner

离线漏斗从最便宜、最安全的证据开始，逐层向真实执行靠近：

```text
GT 数据
  -> 模型 raw action
  -> 时序连续性
  -> action pipeline
  -> 最终将发送的动作
  -> 实机
```

### 1. GT 本身是否合理

先检查训练数据相邻动作的幅度。

- P511 的 GT 相邻臂动作 p50 约为 `0.007-0.012 rad`。

这说明真实遥操数据的控制节奏是连续的小步变化，而不是 `0.4 rad` 量级的跳变。因此，如果模型 raw action 出现约 `0.41 rad` 的变化，不能简单归因于“遥操作数据本来就抖”。

### 2. 模型是否学到关键任务语义

选择确定的 GT 状态作为输入，例如 P365 episode 4 frame 50；frame 50-54 是明确进入抓取/合手的区间。

**HEX 30k：**

- GT 需要抓取；
- HEX 对同一训练场景不输出抓取。

结论：问题 owner 基本锁定在模型、checkpoint 或训练配方，不是机器人执行层。

**Psi0：**

- frame 50 有明显 grasp；
- frame 50-54 连续有 grasp。

结论：Psi0 通过了“是否学到抓取语义”这一关。

### 3. raw action 是否具有正常的时间结构

这一层不只问“动作方向对不对”，还要问“动作序列是否像真实机器人可执行的轨迹”。

P511 50k 的现象是：

- 抓取存在；
- 预备位重新出现；
- raw arm delta 仍约为 `0.41 rad`；
- GT 相邻变化约为 `0.01 rad`。

这意味着语义可能是对的，但控制时间尺度可能不对：模型可能知道应该伸手、抓杯，却以“一步跳到未来姿态”的方式表达，而不是每个 control tick 给出小而连续的动作。

### 4. action pipeline 是否破坏了模型意图

需要逐段核验以下链路：

```text
raw model action
  -> decode
  -> absolute/relative conversion
  -> chunk/action horizon
  -> interpolation
  -> slew limit
  -> joint limit
  -> command sent
```

Psi0 的 slew dry-run 已确认：

- raw 最大动作约 `1.29 rad`；
- slew 后 `final_sent_Ri0 ≈ 0.68`；
- 抓取没有被 slew 删除。

因此，Psi0 的抓取问题不能简单解释为“限速器把抓取吃掉了”。接下来应检查：

- 训练 action horizon；
- inference 每次实际执行 chunk 的多少步；
- 是否应只取第一个 action；
- 未来 waypoint 是否被 runner 当成下一 tick；
- control Hz 与 dataset Hz 是否一致；
- normalization 与 delta 的定义；
- temporal ensemble；
- action chunk 是否被重复刷新。

离线漏斗的价值在于：不让“实机表现不好”变成无法定位的问题黑盒。

## 二、决策漏斗：决定下一步行动

决策漏斗不负责诊断模型内部，而是根据离线证据决定继续训练、采集、改 pipeline、上机或停止。

### 1. 关键任务语义有没有学到？

若模型在训练 GT 的关键帧都不抓：

```text
不上机
```

HEX 30k 属于这种情况。它连 teacher-state 离线验证都没有通过，调整机器人 runner 没有意义。

若模型在训练关键帧可以稳定输出抓取：

```text
进入下一关
```

Psi0 当前属于这一分支。

### 2. 动作是否控制级合理？

检查：

- 相邻动作幅度；
- 方向反转次数；
- wrist/shoulder 高频跳变；
- chunk 内部轨迹；
- 与 GT 时间尺度的差距。

当 GT 约为 `0.01 rad`、模型约为 `0.4 rad` 时，不应先问“再训练 10k 能不能解决”。应优先核对 action representation、action horizon、execution budget 与 temporal contract。

### 3. 是否属于模型容量或训练不足？

只有确认训练到推理的合同正确后，才评估：

- 30k -> 40k -> 50k 是否持续改善；
- loss 与 validation；
- grasp accuracy；
- trajectory smoothness；
- onset timing；
- state-conditioned consistency。

如果上述核心指标随训练持续改善，可以继续训练。

但 P511 50k 目前不是这个干净结论：抓取与预备位改善了，但 raw action 仍很大，且部分关节存在反向跳变。因此不能直接推论“模型明显没训够，继续到 60k 就会好”。

### 4. 是否真的缺数据？

只有能够明确指出缺失的数据段，才值得继续采集。

例如，若后续证据显示：

- 接近杯子可以；
- 抓杯可以；
- 但从端杯切换到倾倒时频繁失败；

那么应补充：

```text
端稳 -> 倾倒 onset -> 倒药 -> 回正
```

而不是随机增加 200 条完整 episode。数据采集必须解决已经定位的问题，不能只把数据量从 511 条增加到 700 条。

### 5. 何时允许上机？

只有同时满足以下条件，才进入实机 gate：

```text
语义正确
  + 连续动作合理
  + pipeline 合同确认
  + slew 后仍保持任务意图
  + 初始状态稳定
```

执行顺序固定为：

```text
dry-run -> supervised physical run -> 完整任务
```

## 三、当前结论

### HEX 30k

**离线漏斗：**

```text
GT 有抓取
  -> HEX raw 没抓取
  -> 无需继续排查 pipeline
```

**决策：**

```text
不上机 -> 不改机器人 -> 检查训练/checkpoint
```

### Psi0 P511 50k

**离线漏斗：**

```text
GT 有抓取
  -> Psi0 有抓取
  -> 预备动作存在
  -> slew 后抓取仍存在
  -> raw temporal movement 远大于 GT
```

当前矛盾集中在时序、action pipeline 或动作表达。

**决策：**

```text
暂不盲目继续堆到 55k/60k
  -> 暂不急于大量采数据
  -> 先查清 action 时间合同
  -> 合同正确后，再判断是训练配方问题还是针对性数据缺口
```

## 四、执行原则

错误循环是：

```text
实机失败 -> 怀疑数据少 -> 再训练 -> 再上机 -> 又失败 -> 再采数据
```

正确流程是：

```text
实机或离线发现异常
  -> 精确定位异常所在层级
  -> 只修改该层
  -> 离线重新验证
  -> 通过后再进入下一层
```

这能减少 G1 实机试错。

按当前证据，Psi0 尚不能得出“不适合端药杯倒药”的结论。相反，它已经比 HEX 更早跨过关键门槛：它至少理解了什么时候应该抓。当前需要回答的核心分叉是：

> Psi0 是不会控制，还是其输出 action 被用错了时间尺度？

在这个问题澄清前，不应盲目增加训练步数、增加采集量或扩大实机尝试。

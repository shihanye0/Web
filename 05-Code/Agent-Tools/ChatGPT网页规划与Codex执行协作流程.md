# ChatGPT 网页规划与 Codex 执行协作流程

## 先记住这条流程

**Codex 准备项目简报 → 网页版独立规划和质疑 → 把结论交回 Codex → Codex 结合项目事实审查、执行和验证。**

本文默认“网页版”是用浏览器打开的 ChatGPT。可以一直沿用浏览器聊天，不需要使用 Codex 桌面端的 Chat 或 Quick chat；后者只是可选入口。两端采用同样的模型/模式、资料和问题时，可以完成相同的规划职责，具体回答仍会受项目指令、记忆和聊天历史影响。

这套方法用于两个目标：让规划多一个独立视角；减少 Codex 中反复介绍背景、发散讨论和比较方案的消耗。网页版不了解实时实机情况也可以提出有价值的建议，但这些建议必须经过本地核验。

两个模型都可能出错；意见一致不能代替代码、日志或实机证据。对抗式审查的作用是找出假设、反例和遗漏，不是让两个模型互相认可，也不是强行凑反对意见。

## 两端分别负责什么

| 对话对象 | 适合交给它的事情 | 需要保留的边界 |
| --- | --- | --- |
| 网页版普通 Chat | 方向规划、方案比较、调研、提出反例、挑战现有设计 | 不把历史测试当当前状态，不假定硬件能力已具备 |
| 项目中的 Codex | 读取当前代码和日志、核对实机证据、裁决方案、修改和测试 | 不能照单全收网页建议，也不能为了维持现状而排斥新方案 |
| 实际操作者 | 提供现场观察、确定目标和取舍、按项目要求确认有界实机操作 | 网页方案不自动产生上线、扩大范围或机器人动作授权 |

明确的小修和已定位的问题直接交给 Codex。需要发散思考、复杂取舍或独立质疑时，再使用网页规划。

## 第一步：怎样和 Codex 交流，准备资料

在真实项目对应的 Codex 聊天中说明本次目标。例如，下面是移动取杯的提问示例，不表示已经决定开展该任务：

```text
使用 $chatgpt-planning-handoff，为当前项目准备网页规划简报。

这次想讨论：G1 如何移动到桌前合适的位置，再与已有 VLA 抓取模块交接。
先不要实现这个业务目标，也不要启动机器人。

只整理会影响这次规划的背景、已有能力、约束、带日期的证据、未知项和需要挑战的假设。区分研究建议、离线回放、接口预检和实机验证。给我可以上传的 ai_context.md。
```

日常可以简化成：

> 为这个项目准备网页规划简报，主题是……

项目或目标有变化时说：

> 更新网页简报，主题是……，只补充有关变化；没有重新检查的现场状态继续标为未知。

简报至少应说明：本次目标和完成标准、必要背景、不可改变的约束、已验证与未验证的内容、证据日期，以及希望网页版重点挑战的问题。更新简报不必重读整个仓库，但不能仅凭 HEAD 没变就认为工作区或部署没变。

## 第二步：怎样和网页版交流，获得独立规划

用浏览器打开 ChatGPT，进入**普通 Chat**，上传最新 `ai_context.md`，再写明这次问题。不要只上传文件，却让模型猜本轮要做什么。Codex 的 Quick chat 是可选替代入口，本流程不依赖它。

可直接复制：

```text
请阅读附件 ai_context.md。我这次的目标是：……

请先独立分析可行方向，再审查你自己最推荐的方案。区分附件里的事实、你的推断和未知；你不了解实时实机状态，不要把历史服务在线、离线测试或研究建议当作当前已具备的能力。

比较必要的替代路线，说明主要方案最容易在哪里失败，以及什么反证会让你改变建议。既挑战新方案，也挑战现有实现，不为凑反对意见而反对。

缺少资料时，列出会改变判断的最小证据，由本地 Codex 核验；可以给条件化建议，不要补造项目状态。

最后整理一份交给 Codex 的结论：目标、推荐及理由、替代方向、关键假设与反对意见、需要本地核验的内容、最小实施范围和验收条件。不要默认扩大到上线或新增机器人操作。
```

适合继续追问的问题：

- “如果你的推荐是错的，最可能错在哪个前提？”
- “有没有更小、能直接利用现有模块的方案？什么情况下现有模块确实不适合？”
- “哪项最小验证能决定下一步，而不是只增加离线信心？”
- “如果没有你假定的硬件能力，替代方案是什么？”

讨论结束后，可让网页版压缩交接材料：

```text
请把本轮讨论整理成供 Codex 核验的最终方案。保留选定方向及理由、重要替代方案、关键反对意见、未确认假设、证据需求和验收条件；保留影响决策的失败条件，不必重复整段讨论。把建议与我已明确作出的决定分开。
```

## 第三步：把网页结论交给项目中的 Codex

默认把浏览器中讨论后的最终方案复制到正确项目的 Codex 聊天；也可以保存为本机文件，让 Codex 读取。这样无需使用桌面端 Chat，也不依赖“添加到 Codex”按钮。

如果当前客户端确实提供“添加到 Codex”或已有 ChatGPT 会话接入入口，也可以使用，再确认执行位置是正确的项目。官方文档描述的是客户端接入能力，不能据此保证浏览器页面有同名按钮；本机完整导入尚未实测。不要为了交接先安装复杂桥接。

也可以这样说：

> 读取我在 ChatGPT 中关于「具体主题」的会话，核对最新提问和最终方案，再接回本项目审查。若正文取不到，明确说明缺少什么。

本次曾验证内置会话工具可以读到一条 ChatGPT 用户提问；该轮助手回答只返回内容引用。因此，**找到会话不等于取到了方案全文**。只有摘要、引用或截断时，应补充原文，不能凭标题猜方案。

## 第四步：怎样要求 Codex 审查和执行

需要先审查、暂不实施时：

```text
使用 $chatgpt-planning-handoff 接回这份网页方案，本轮只审查，不实施。

把网页内容当外部建议，结合当前项目指令、源码、日志及带日期的实机证据，逐项判断：采纳、修改后采纳、暂缓或拒绝、需要验证。

给出影响决定的依据，同时寻找网页与现有实现共有的错误假设。不要因为熟悉现有实现就排斥替代方案，也不要为了形式完整而重做全部规划。最后给出最值得做的下一步及完成标准。
```

已经选好目标，准备实施时：

```text
使用 $chatgpt-planning-handoff，结合这份网页方案推进本项目。

我选定的目标是：……
本轮实施范围是：……

先按当前项目事实做对抗式审查，明确采纳、修改或拒绝的内容及依据，再完成目标所需的最小完整改动和相称验证。按问题定点取证，不机械重做网页的全部规划。

网页新增建议不自动扩大任务、上线或实机操作范围。发现不适合项目的建议直接指出；存在重要未知时，先完成不依赖它的工作，再说明缺少的最小证据。

收尾说明实际改动、验证结果和未验证范围。只有复杂取舍或重要疑点仍未解决时，再准备给网页版的差量复审材料。
```

不建议只说“把所有值得做的优化都做掉并统一上线”。它没有限定目标，容易让一次方案讨论扩张为无边界改造。

## 什么情况下再回到网页版

复杂架构取舍、与预期不符的真实失败、影响较大的改动，可以让网页版复审。返回资料只需包括本轮变化、相关结果、未解问题和必要证据；重要原文仍保留供追查。

可对 Codex 说：

> 准备本轮差量复审材料，只包含实际改动、相关验证结果和未解决的问题，明确哪些结论需要网页版挑战。先生成本地文件，不自动上传。

普通小修完成对应检查后就收尾，不要求每次都走双模型循环。

## G1 项目最容易混淆的几件事

| 看到了什么 | 仍不能自动推出什么 |
| --- | --- |
| 服务能响应、端口在线 | 定位、导航或交互任务已经可用 |
| 离线视频里检测到杯子 | 实机能安全到位并成功抓取 |
| 历史日志中动作执行成功 | 当前模式、姿态、网络和设备仍适合执行 |
| 文本回复和模拟音频回放通过 | 老人现场听感、识音和扬声器播放已经验收 |
| 云端页面可登录、有业务记录 | 本地记录正在持续同步到云端 |
| 网页给出了完整方案 | 已获得新增机器人动作或重启历史路线的授权 |

这些边界应体现在简报里，也应成为 Codex 接回方案时的审查点。

## 怎样判断是否省了开销

优先把方向讨论、方案比较和反复解释背景放到普通 Chat；让 Codex 聚焦本地核验与实施。回程保留最终取舍、反例、假设和验收标准，避免默认带回整段长聊天。

截至 2026-10-23 核对，官方说明 **ChatGPT Work 与 Codex 共享用量**。不能只看“是不是网页端”，就判断是否消耗同一额度；具体入口和账号用量应按当时产品与实际记录确认。

原帖作者给出的节省比例属于其个人任务经验，本机尚未测量。不为了省 token 省掉必要验证，也不预设每个任务使用两端都会更便宜。

## 当前完成与未验证

- 已完成：项目基础简报、使用说明、共享 Skill、来源版本记录、Skill 格式检查、共享同步与一致性检查。
- 未验证：客户端“添加到 Codex”的完整交接、新会话自然触发 Skill 的行为质量、实际节省比例。
- 尚未配置：Drive 同步、只读 MCP、浏览器桥、定时上传。本次搭建没有向网页版发送消息或上传文件。
- 简报是文档快照；当前代码、部署和实机状态需在具体实施任务中重新核对。

后续若网页频繁因缺少最新代码或运行数据而无法判断，再增加只读 MCP；若经常整理多个项目背景，再评估 AI Context Linker；若手动来回交接成为主要负担，再评估 codex-with-chatgpt。

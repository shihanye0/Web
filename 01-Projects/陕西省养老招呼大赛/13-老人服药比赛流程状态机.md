## 3. 谁在干什么

| 层 | Owner | 实机在做什么 |
|---|---|---|
| 何时开 A / 是否自动开 B | 我们的 reducer + live bridge | 一次确认后 exec A；三条 A 事实过了再 exec B |
| A 倒药、放瓶、ESC3 | 隔离副本里的队友脚本，打 `127.0.0.1:8797` | p593 mixed **155000**，`--task pour` |
| B 递橙 + 12 秒桥 | 同一隔离客户端的另一 launcher，打 `127.0.0.1:8798` | p1156 mixed **175000**，`--task handover`，`HND_FB=1` |
| 切 B 时回到预备位 | **队友 B 脚本 PREPOSE**（A 收尾还有 ESC3） | 不是状态机发回零位 |
| 倒药成功 | **队友脚本腕角**：命令 `R-WR < -0.8` 再抬回，然后可能 0.5s 后脚本放瓶 | 不是视觉、不是「药粒进杯」 |

训练上是混合模型 + 不同指令；**上机是两个 checkpoint、两个端口**。175000 倒药会回归，所以 08-31 双路由定案：倒药守 155000，递橙用 175000+桥。状态机只是换 launcher / 换服务，不是一个权重上改 prompt。

隔离目录 `scripts/p425_team_fsm_stage_bridge_r1/` 是 `/home/user/hby/deploy_a185` 的复印件（加确认门闩和 A 结果 JSONL），**不改队友本体**。

## 4. A/B/C 主流程（合同）

```text
SESSION_STARTED
  -> A：抓取粉色药瓶并倒药（runtime 事实）
     -> 药瓶放到桌面右侧（runtime 放瓶例程）
  -> B：右手递橙色药杯（开场固定橙杯点，不重新视觉确认）
     -> 老人接走
     -> 右臂回初始位
     -> 橙杯稳定回桌
  -> C：左手递蓝色水杯
     -> 老人接走
     -> 左臂回初始位
     -> 蓝杯稳定回桌
  -> 最终场景确认
  -> FLOW_COMPLETED
  -> REQUEST_SUCCESS_ANNOUNCEMENT
```

当前 live 入口只自动串到 B 启动。B 进程退出 ≠ B 交接成功，也不进 C。

`A_POUR_EXECUTION_FINISHED.success=true` 只表示有界倒药**动作例程**结束，不是观察到药粒落入橙杯。橙杯不透明时，也不要用「杯内可见药粒」做开 B 否决；那会把自动链卡死，且现网没有可用的 v3 实机视觉入口。空杯否决若以后做，仍应全自动（视觉进程出事实，reducer fail-closed），不是终端手动确认。

## 5. 失败与恢复

- A 抓取 / 倒药例程 / 右侧放瓶任一 `success=false`：不开 B，停在人工复位（现场收拾场景，不是软件弹窗）；
- A 进程非 0 退出、结果头缺失、180 秒到期：不开 B；
- B/C 掉杯或 runtime safety fault：立即停止并等待人工复位（合同语义；B/C 完成事实尚未接进 live）；
- 全流程最多 180 秒，从 A 结果文件头起算。A 最长约 120 秒，B 最长约 90 秒，A 拖满时 B 可能被全局死线裁掉。

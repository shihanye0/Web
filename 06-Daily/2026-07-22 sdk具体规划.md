## 一、执行摘要

项目原计划逐步走向“控制计算机识别黄色杯子并控制灵巧手触碰”。随着遥操采集成为后续训练数据的主要来源，这条路线暴露出职责偏移：SDK 负责人开始承担视觉、任务策略和自主动作，而真正影响遥操与训练的数据合同、动作合同、runtime 门禁和统一 episode 尚未形成。


本次重规划将唯一主线冻结为：

> SDK 贯穿真实 G1/Dex3 接入、遥操采集、训练数据生成、策略接入、部署执行和运行诊断，为所有上层提供统一、可验证、可回放的观测—动作边界。

> 📘 **解释：“观测—动作边界”是什么意思？**
> 这是一个**数据契约（Contract）**的边界。左边（上游）是遥操设备或 AI 策略，右边（下游）是真实机器人。SDK 在中间做唯一通道：
> - **观测边界**：统一输出 `ObservationFrame`（含 LowState、IMU、RGB、Dex3 触觉等），所有上层只读这个，不直接读 DDS topic。
> - **动作边界**：统一接收 `ActionFrame`（含目标关节角度、速度、力矩等），所有上层只写这个，不直接写电机 cmd。
> 
> 好处是：上层换算法、换遥操设备，SDK 的接口**纹丝不动**。

历史 Gate 全部保留为证据，但后续产品路线改由 SDK 生命周期门禁驱动。当前阶段从“继续触杯实验”切换为“遥操设备到货前 SDK 核心”。

> 📘 **解释：什么是“Gate”？为什么叫“历史 Gate”？**
> “Gate” 是项目执行过程中设立的**阶段性验收关口（Gate）**，每个 Gate 对应一组实机测试证据（日志、截图、数据记录），证明某块能力“在真实机器人上跑通了”。本项目历史上有 Gate0 到 Gate38，但现在这些 Gate 被**降级为历史证据**，不再继续扩展（因为触杯演示路线被叫停），改为由新的 SDK-R0~R6 门禁驱动产品路线。

## 二、为什么需要调整

行为克隆或策略训练要学习的是：

```text
observation_t -> action_t
```

> 📘 **解释：行为克隆（Behavior Cloning）的基本公式**
> 这是模仿学习的核心：在时刻 `t`，机器人看到什么状态（`observation_t`），遥操专家做了什么动作（`action_t`），模型就学习这个映射关系。训练数据中**必须同时存在 observation 和 action**，缺一不可。

此前人工搬动手臂触杯主要记录 RGB、LowState、Dex3 状态和压力。它验证了 observation、采集和接触信号，却缺少遥操系统发出的 raw action、映射动作和最终 SDK command，因此无法代表主要遥操训练数据。

> 📘 **解释：缺了什么关键数据？**
> 人工搬动手臂时，**人的手臂就是控制器**，没有“遥操设备”产生 `action` 信号。因此录下来的数据只有 `observation` 没有 `action`，训练模型时**没有输入（action）怎么学映射**？所以 Gate38 只能算是“诊断样本”，不能作为大规模训练数据使用。

继续沿自主触杯路线会产生三类偏差：

1. SDK owner 被视觉检测和任务决策侵入；
2. 遥操到货后仍需重新建设动作合同与数据格式；
3. 采集路径和未来策略部署路径可能形成两套门禁与命令语义。

调整后的原则是先完成共享基础，再接具体设备和任务。

## 三、SDK 负责部分的最终目标

SDK 子系统最终交付一套全生命周期 runtime：

```text
DeviceAdapter / PolicyAdapter
  -> ActionFrame
  -> SdkRuntimeCore
  -> RobotCommandAdapter
  -> G1 / Dex3
  -> ObservationFrame + ExecutionResult
  -> Episode / Replay / Dataset Export
```

> 📘 **解释：这张数据流图的详细拆解**
> - **DeviceAdapter**：遥操设备（如 3D 鼠标、VR 手套）的驱动适配器，把设备原始信号转成 `ActionFrame`。
> - **PolicyAdapter**：AI 策略（如神经网络输出的动作）的适配器，也转成同样的 `ActionFrame`。
> - **ActionFrame**：统一的动作指令格式（关节目标、速度、力矩……）。
> - **SdkRuntimeCore**：调度引擎，负责频率控制、超时、去重、deadman 心跳等。
> - **RobotCommandAdapter**：把标准 `ActionFrame` 翻译成宇树官方 SDK 或 DDS 能认的底层 cmd 消息。
> - **G1/Dex3**：物理机器人执行动作。
> - **ObservationFrame + ExecutionResult**：执行后的状态反馈（LowState、RGB、触觉、执行回执）。
> - **Episode**：从开始到结束的一整段 <Action, Observation> 序列容器。
> - **Replay / Dataset Export**：回放验证 + 导出为训练数据集。

SDK owner 负责：

- 官方 SDK/DDS/ROS 2 接入与版本/profile 事实；
- Observation、Action、ExecutionResult、Episode 合同；
- 校验、限幅、deadman、超时、模式门禁、释放和恢复；
- G1/Dex3 命令执行、状态回读和诊断；
- 遥操设备 adapter 接口与到货后的具体接线、标定；
- raw input、mapped action、sent command、result、observation 的统一记录；
- 训练数据导出与策略部署接入同一 runtime。

> 📘 **解释：为什么强调“raw input”和“mapped action”都要记录？**
> 训练时需要的 `action_t` 是“经过映射和标定后的目标值”，但调试时经常需要回溯“遥操设备原始值 vs 映射后目标 vs 最终发送给电机的 command”三者是否一致。三者都记录，**排错时可以从源头追到尾**，不需要猜。

相邻 owner：

| 层 | Owner |
|---|---|
| 遥操交互 | 设备交互体验、操作者流程 |
| 视觉 | 检测、跟踪、空间估计 |
| 训练 | 模型、损失、训练过程、权重 |
| 策略 | 任务决策、接近、接触、抓握、撤离 |
| SDK | 真实机器人观测、动作执行、门禁、记录、回放 |

所有上层都通过 SDK 合同连接真实机器人。

## 四、目前已经完成什么

### 4.1 通信与观测

| 能力 | 实机证据 | 状态 |
|---|---|---|
| 网络 | `enp3s0` 与 G1 4/4 ICMP | 通过 |
| DDS / SDK 状态 | `rt/lowstate` 60 秒 62,465 条，`1041.525 Hz` | 通过 |
| 状态产品层 | 60 秒 62,490 条、异常与事件丢弃为 0 | 通过 |
| ROS 2 同源 | 与 SDK 频率差 `0.312%` | 通过 |
| Dex3 direct-state | 约 `794 Hz`，7 电机和 9 组压力可记录 | 通过读取 |
| 前视 RGB | RTP/H.264，`1280x720x3` 真彩色新帧 | 通过 |

> 📘 **解释：这些指标代表什么？**
> - `1041.525 Hz`：LowState 更新频率约 1kHz，说明 SDK 能拿到高频关节状态，满足控制实时性要求。
> - `异常与事件丢弃为 0`：数据接收层没有因为队列满或处理不过来的丢帧，说明当前负载下 SDK 处理能力充足。
> - `0.312%` 频率差：ROS 2 桥接层与原生 DDS 频率几乎一致，无显著失真。
> - Dex3 约 794 Hz：灵巧手的状态反馈也足够快。
> 
> 这些是“地基”性质的证据，证明**真机通信链路是健康的**。

### 4.2 请求、runtime 与生命周期

- `ServiceList`、`GetVolume`、固定 TTS 有实机证据；
- intent、幂等、速率门禁和 JSONL runtime 已形成可测试 owner；
- 服务 close/restore、subscriber callback 排空与有界日志已有实现模式。

> 📘 **解释：什么是“幂等”、“速率门禁”、“JSONL runtime”？**
> - **幂等**：同一个请求发送多次，副作用只发生一次。防止网络重发导致机器人重复执行危险动作。
> - **速率门禁**：限制每秒最大请求数，防止策略输出频率过高冲垮底层通信。
> - **JSONL runtime**：每一行是一个 JSON 对象的日志格式，便于按行流式解析和回放。
> 
> 这些能力从产品主线降级为 SDK RPC/runtime fixture，代码继续保留。

### 4.3 Dex3 右手

- `rt/dex3/right/cmd` 本机 writer、source/direct-state/post 和 episode 路径已验证；
- 右手最多观察到 6/7 逻辑关节沿预期方向响应；
- `thumb_0` 只有亚阈值方向证据，仍未形成可控结论；
- Gate10 第二段未证明在窗口内返回 source。

> 📘 **解释：“亚阈值方向证据”是什么意思？**
> 给拇指发送了动作指令，拇指有微弱的响应（比如动了 0.5 度），但达不到预期幅度（比如目标 10 度）。这种“动了但没到位”的状态就叫亚阈值。可能原因：力矩限制太低、机械卡滞、或该关节有特殊保护逻辑。需要进一步确认。

结论：右手 adapter 和取证基础可复用，完整 profile 能力仍是 partial。

### 4.4 右臂

- 官方 action、服务状态、current-pose hold、release/restore 和有限 transport 均有证据；
- Gate27 当前位保持完整；
- Gate28 系列 writer transport 完整，post 未观察到冻结阈值响应；
- 当前阻尼状态下 ArmAction 返回 `7404`，体现模式依赖。

> 📘 **解释：“返回 7404”是什么意思？**
> `7404` 是宇树 SDK 某种状态码（具体含义需查官方文档），在阻尼模式下出现，说明 ArmAction 的返回受当前机器人模式影响。这提醒我们：**同一段 ActionFrame，在不同模式下可能得到不同行为**，必须在合同里显式声明“当前模式”字段。

结论：服务生命周期和 transport 可复用，连续遥操动作采纳尚未闭合。

### 4.5 数据链

- JPEG/JSONL/summary/SHA-256、direct-state、LowState、压力、command intent/result 和离线时间关联均已有 owner；
- Gate11--13 验证了一条候选视觉—状态—固定动作链；
- Gate38 重录完成 RGB 676 帧、LowState 46,844 条（`1041.555 Hz`）和 Dex3 4,191 条，操作者确认触杯、杯体无明显位移且全程无异常。

Gate38 的最终定位是 SDK 多模态采集、提示时序、接触信号和人工标注资格证据。接触窗口可见操作者扶杯，因此“杯体无明显位移”来自操作者标注；其人手介入、缺少遥操 command 和单场景属性决定了它只能作为诊断样本。

> 📘 **解释：为什么 Gate38 不能作为训练数据？**
> 因为训练需要 `(observation, action)` 对，Gate38 只有 observation（RGB + LowState + 触觉），没有 action（操作者扶杯动作没有被任何设备记录为数字信号）。AI 模型无法从“只有结果没有操作”的数据中学习。它只能用来测试“采集管道是否正常工作”。

> 📘 **解释：“右臂执行 transport 级”指什么？**
> “transport 级”表示只验证了“指令能通过网络发出去并收到回执”（writer success），但**没有验证连续多帧指令的物理执行效果**（比如轨迹是否平滑、是否收敛到目标位置）。这是从“能发”到“能动”的差距。

## 六、保留、降级与停止

### 主线保留

- 网络、DDS、ROS 2、状态、模式与版本取证；
- G1/Dex3 RobotAdapter；
- RGB、LowState、Dex3/压力采集；
- episode、回放、时间关联、字段完整性和哈希；
- 服务生命周期、输入门禁、资源上界和错误投影。

### 降级为旁支或 fixture

- TTS、中文意图和护理任务；
- 黄色杯 detector；
- 固定右手/右臂动作 executable；
- Gate38 人工触杯。

> 📘 **解释：为什么“黄色杯 detector”被降级？**
> 黄色杯检测是一个**视觉任务**，属于视觉团队的职责，不应由 SDK 负责人维护。它应该以“外部服务”的形式调用 SDK 的 `ObservationFrame` 来获取图像，而不是成为 SDK 核心的一部分。

### 当前停止

- 继续以固定动作逼近自主触杯；
- 继续增加杯子任务语义到 SDK 核心；
- 在统一 Action/Episode 合同前批量采集；
- 让训练或策略直接访问 DDS topic；
- 为未到货设备预埋厂商私有字段。

> 📘 **解释：为什么要停止“为未到货设备预埋厂商私有字段”？**
> 遥操设备还没到，不知道它的坐标系、量程、单位等细节。现在预埋字段是“猜”，猜错了后面要改合同，导致 Episode 数据格式不兼容，**旧数据全废**。所以先用抽象接口占位，等设备到了再填具体实现。

## 七、重新规划后的路线

### SDK-R0：实机通信与观测基线

状态：已通过。历史 Gate 0--13 与后续读取证据组成当前基线。

### SDK-R1：机器人执行能力矩阵

状态：部分通过。把每条 hand/arm/service 能力标为 verified、partial 或 unknown，禁止从 writer success 外推物理执行。

> 📘 **解释：什么是“能力矩阵”？**
> 一张表格，行是机器人所有原子动作（如“右臂笛卡尔直线运动”、“Dex3 拇指弯曲”），列是测试工况（空载、负载、高速等），格子里填 verified/partial/unknown。它是对外公开的**“机器人身体技能体检表”**，防止虚假宣传。

### SDK-R2：统一合同与 runtime

下一阶段目标：

- ObservationFrameV1；
- ActionFrameV1；
- ExecutionResultV1；
- EpisodeV1；
- SdkRuntimeCore；
- fake device、mock robot、recorded replay。

验收重点是维度、有限值、顺序、重复、deadman、超时、模式、资源上界和 round-trip。

> 📘 **解释：这 9 个验收关键词的含义**
> - **维度**：数组长度固定（如 6 轴机械臂长度必须为 6）。
> - **有限值**：所有浮点数不能是 NaN 或 Inf。
> - **顺序**：字段排列顺序锁定，防止不同版本解析错位。
> - **重复**：相同 seqNum 的帧只执行一次（幂等）。
> - **deadman**：心跳看门狗，断连超时自动刹车。
> - **超时**：指令发出后超时未回执则报错。
> - **模式**：区分 fake/mock/real/replay 模式，不同模式不同行为。
> - **资源上界**：内存、队列、日志都有最大限额，超出则丢弃或报错。
> - **round-trip**：从 Action 发出到 Observation 回来的端到端延迟。

### SDK-R3：Device-adapter-ready

这是遥操设备到货前的完成定义：具体设备 adapter 之外的合同、runtime、记录、回放和机器人能力矩阵全部就绪。

> 📘 **解释：“Device-adapter-ready”≠“全部完成”**
> 它是指“**软件侧全部就绪，只差硬件适配器填空**”。等遥操设备一到，只需写一个 `XxxDeviceAdapter` 类继承抽象接口，把设备的原始读数转成 `ActionFrame`，**不需要改 runtime 核心**。

### SDK-R4：遥操设备接入

设备到货后完成厂商 SDK adapter、坐标/零位/方向/尺度标定、deadman、端到端延迟、抖动、掉线和恢复测试。先做无物体 smoke。

### SDK-R5：遥操数据资格

先采集 10--20 条小规模 episode，验证图像、状态、raw/mapped/sent/result、标签和时间质量，再扩大数据量。

### SDK-R6：训练与部署

训练数据从 EpisodeV1 导出；PolicyAdapter 输出同一 ActionFrame，经同一 runtime、门禁和 RobotAdapter 执行。

## 九、风险与反事实审查

### 阻断问题

- 右臂连续遥操 command 的官方模式、采纳与 watchdog 语义尚未闭合；
- `thumb_0` 仍是 partial；
- 统一 Action/Episode 尚未存在。

### 设计风险

- 设备私有坐标泄漏进核心合同；
- 训练只保存 mapped target，遗漏最终 sent command；
- 遥操采集与策略部署各自建立门禁；
- receive timestamp 被提升为硬件同步；
- 旧 Gate 数字继续驱动产品路线。

### 可记录债务

- 固件版本与部分 reserve/status 字段语义仍未知；
- TTS 请求与播放状态缺少严格请求 ID；
- 历史仓库仍为 unborn、全未跟踪状态。

### 三个月后最可能的失败原因

设备到货后才发现核心合同绑定了错误坐标或缺少 raw/sent action；训练数据与部署输入分裂；机器人模式和超时行为在 runtime 外散落。阻断手段分别是 DeviceAdapter 边界、统一 Episode、统一 SdkRuntimeCore 和 profile 能力矩阵。

先用 fake device 和 mock robot 完成合同与失败路径；随后再接现有 RobotAdapter。该阶段无需遥操设备，也无需新的实机状态变更。

> 📘 **解释：为什么这一步是“最小”且“单独”的？**
> - **最小**：只做 3 个模块，不碰视觉、策略、遥操设备、杯子任务。
> - **单独**：这是一个独立任务，可以在不插真机、不等硬件到货的情况下 100% 完成。
> - **核心价值**：先把“数据合同”和“失败路径”用软件模拟跑通，等硬件来了只做“填入”，不伤筋动骨。

这次的新现象其实把根因又缩小了一层：

**它不是“不会抓”，而是抓取触发条件非常脆弱；它也不是“不会倒”，而是倒药阶段缺少可靠的目标重定位。**

原 launcher 只是持续让 VLA 输出绝对 24D chunk，并没有一个“等抓取命令”的外部状态；`--grasp-timeout 45` 只是给策略很长时间自己产生闭手动作。

### 1. 为什么会“明明已经可以抓，却等很久才抓”

你这次最关键的新证据是：

```text
开始：到达瓶子旁边，但长时间不闭手
后来：突然开始抓
最终：确实 grasp 成功
```

这比之前的 `86 chunks n_close=0` 更说明模型内部存在一个类似：

```text
approach
   ↓
pre-grasp / hover
   ↓
[某个隐含条件满足]
   ↓
close fingers
```

这个“条件”大概率不是脚本条件，而是模型自己学出来的 **隐式 grasp trigger**。

问题在于它的决策边界很窄：

```text
                 learned boundary
                      │
手已经很接近瓶子        │
──────────────────────┼────────────
     不抓              │       抓
 finger≈0.1~0.2        │    finger≈1.0
```

你肉眼觉得：

> “现在和十几秒后几乎一样，为什么现在不抓？”

但对模型来说，可能只是几个很小的变化：

- 腕姿态改变几度；
    
- 瓶子在图像里移动几像素；
    
- 手对瓶子的遮挡比例变化；
    
- finger proprio 变化一点；
    
- 相机抖动；
    
- arm 因 absolute target 慢慢漂到另一个状态；
    

最终某一帧刚好跨过决策边界，它才突然输出 closure。

因此你感受到的“犹豫”非常像一个 **pre-grasp fixed point + 不稳定 escape**：

```text
image: 手已经在瓶边
state: 手已经在瓶边
        ↓
policy: 再保持一下
        ↓
机器人几乎不动
        ↓
下一帧还是同样画面
        ↓
policy: 再保持一下
        ↓
      循环很多次
```

直到微小视觉/状态扰动让模型跳出去：

```text
hover → CLOSE
```

### 2. 这个问题不能靠缩短 timeout 真正解决

例如把：

```bash
--grasp-timeout 45
```

改成：

```bash
--grasp-timeout 10
```

只会让失败更快。

不会让模型更早闭手。

同样：

```text
降低 0.55 grasp latch
脚本强制闭手
看到手靠近就自动 pinch
```

都会把“模型什么时候认为应该抓”这个真正问题隐藏掉。

所以 FSM 只能负责：

> **不要浪费现场时间。**

不能负责：

> **让策略学会及时抓。**

# 3. 我现在最建议增加一个指标：`time_to_first_close`

你已有：

```text
n_close
Rfinger_max
wr_min
n_pour
```

再补两个非常关键的统计：

```text
GRASP_ENTER → first raw Rfinger > 0.55
GRASP_ENTER → first measured finger > 0.55
```

例如：

```text
[FSM] GRASP enter t=8.42
[POLICY] first_close_target t=27.91 latency=19.49s
[GRAV] bottle grabbed t=28.34 latency=19.92s
```

这样“犹豫”就从主观感觉变成明确指标：

```text
grasp decision latency = 19.5 s
```

未来可以直接比较：

```text
好 run：  1.4 s
坏 run： 22.8 s
坏 run： timeout
```

这个指标对于定位模型问题会非常有价值。

# 5. 这次“会倒，但没找到橙色杯子”其实和不抓很可能是同一个根因

这是我觉得现在最重要的一点。

你目前已经观察到两个 transition 问题：

```text
REACH / HOVER
      ↓
    GRASP
```

发生得很迟。

以及：

```text
GRASP / HOLD
      ↓
MOVE TO CUP / POUR
```

发生了，但**目标定位明显不可靠**。

这不像两个独立的执行 bug，更像模型学成了：

```text
动作阶段本身会做
但“什么时候切阶段”和“阶段切换时应该绑定哪个视觉目标”
不够可靠
```

换句话说，模型可能很擅长 trajectory prior：

```text
伸手
握
抬
翻腕
```

却不够擅长：

```text
确认瓶子现在真的在手里
确认橙杯现在在哪里
移动到杯子上方
确认位置正确
再 pour
```

这就解释了你描述的：

> “这次有倒药动作，但是倒的时候好像没看到橙色杯子的位置，直接倒了。”

这非常像 **动作先验压过视觉闭环**。

# 6. 要先确认：倒的时候杯子到底有没有进入模型 observation

这一项非常关键。

在第一次出现：

```text
n_pour > 0
```

的那个 request 上，直接保存**真正发给模型的图像**。

不要只看机器人现场，也不要只看 run 开头的 `live_probe.jpg`。

看：

```text
first n_pour request image
```

然后问题立即一分为二。

### 情况 A：橙色杯子根本不在模型图像里

那根因不是“模型看见了还找错”。

而是：

```text
camera/FOV/遮挡
   ↓
抓起来后瓶子或机械臂挡住 cup
   ↓
policy 仍依靠 learned pouring trajectory
   ↓
blind pour
```

这时应该修：

- 相机视角；
    
- 杯子摆位；
    
- 抓起后的 observation；
    
- 训练时的 camera geometry；
    
- 多视角输入。
    

### 情况 B：杯子清楚地在图里，但模型仍然朝错误位置倒

那就是很直接的 **visual grounding / target localization failure**。

这时候重点应该是训练数据：

```text
瓶子已经抓住
+
杯子在不同位置
+
必须先移动到杯口
+
再翻腕
```

而不是更多“完整任务从头到尾”的轨迹。

# 7. 我尤其建议做一个非常简单的“移动杯子测试”

这是判断模型究竟有没有真正用视觉定位 cup 的高信息量实验。

机器人已经抓住之后，先不要让它执行真实动作，离线/安全 query policy。

准备三种图像：

```text
A: cup 在左
B: cup 在中
C: cup 在右
```

保持：

```text
机器人 qpos 相同
瓶子姿态相同
task 相同
```

只改变杯子位置。

比较模型接下来输出的腕/臂 target。

正确的视觉闭环策略应该表现出：

```text
cup left  → target left
cup center→ target center
cup right → target right
```

如果输出几乎不变：

```text
A ≈ B ≈ C
```

那就很危险，但也非常有诊断价值：

> **模型的 post-grasp 行为主要依赖 memorized trajectory，而不是根据 cup 当前像素位置做视觉 servo。**

这比单纯看“这一场倒偏了”更能说明问题。

# 8. 同样可以对 grasp 做一个“瓶子移动测试”

固定 qpos。

只改变瓶子图像位置：

```text
左 1 cm
原位
右 1 cm

近 1 cm
原位
远 1 cm
```

记录：

```text
Rfinger_max
n_close
arm target
```

很可能你会看到类似：

```text
位置 A → Rfinger=0.18
位置 B → Rfinger=0.21
位置 C → Rfinger=1.10
```

如果是这样，就找到“为什么它一直等”的直接证据了：

> **并没有在等待代码事件，而是在等待 observation 自己进入一个很窄的 learned grasp region。**

# 9. 从模型层，最有价值的修复是强化 transition，而不是整条任务重新学

如果数据可以重训，我会重点补两类数据。

**第一类：hard grasp-transition samples**

专门收：

```text
手已经正确来到瓶子旁
finger 仍然 open
下一步就应该 close
```

而不是大量：

```text
远处 → 慢慢伸手 → 抓 → 倒
```

因为“伸手”它已经会了。

要密集覆盖：

```text
±1 cm
±2 cm
不同腕角
不同光照
不同遮挡
```

让 close decision 从：

```text
很窄的一条边界
```

变成：

```text
一个宽的 grasp basin
```

也就是进入合理抓取区域之后，都应该稳定闭手。

---

第二类是 **post-grasp cup-conditioning samples**：

```text
瓶子已在手里
杯子左/中/右
杯子近/远
```

训练目标必须明显不同：

```text
先对准杯子
再翻腕
```

这样才能迫使模型学：

```text
pour trajectory = f(current cup position)
```

而不是：

```text
pour trajectory ≈ memorized average trajectory
```

---

# 10. 长期如果能改模型，我会考虑显式 phase conditioning

目前的现象越来越像：

```text
模型既要自己猜 phase
又要生成 24D
```

所以它在关键 transition 上犹豫。

可以让高层只提供：

```text
REACH
GRASP
TRANSPORT
POUR
```

这种 phase condition。

注意这和“脚本替模型闭手”完全不同。

仍然是：

```text
phase=GRASP
   ↓
model → 24D finger + arm
```

而不是：

```text
FSM → finger=1.0
```

这样保留了策略本身完成动作的真实性，同时大幅降低：

```text
“我现在是不是该抓？”
```

这种隐式 phase inference 的难度。

## 我会把现在的问题归纳成两个核心指标

以后每个 run 不用先看“成功/失败”，先看：

```text
1. grasp decision latency
   GRASP enter → first n_close

2. target-conditioned pour
   cup position变化 → predicted pour target是否跟着变化
```

如果第一个不稳定：

> 修 grasp transition robustness。

如果第二个基本不随杯子变化：

> 修 post-grasp visual grounding。

而 **FSM 当前最应该做的事情只是记录和早停，不应该替模型做任何抓取或倒药动作。**

你这次能最终抓住、还能输出真实 `n_pour`，反而说明底层动作能力是存在的。现在真正缺的，是把“偶尔触发正确动作”变成 **基于当前 observation 稳定、及时地触发正确动作**。

你下一步最值得先做哪一个：**A 抓前 5 秒对比**、**B 杯子左右移动测试**、还是 **C 两个一起做**？

# ASPIRE: Agentic Skill Discovery for Robotics

> [!info] 论文信息
> - **全称**：ASPIRE（Agentic Skill Programming through Iterative Robot Exploration）
> - **作者**：Runyu Lu、Yubo Wu、Ethan Kou 等
> - **机构**：NVIDIA、密歇根大学、UIUC、UC Berkeley、CMU
> - **时间**：2026 年 6 月
> - **项目主页**：https://research.nvidia.com/labs/gear/aspire/
> - **本地 PDF**：`/home/user/Downloads/paper/Aspire-dual.pdf`
> - **阅读状态**：已读完
> - **关键词**：Code-as-Policy、机器人编程智能体、持续学习、技能库、执行轨迹、演化搜索、Sim-to-Real

## 一句话概括

ASPIRE 把机器人编程改造成一个持续运行的“编写程序—执行—读取多模态轨迹—定位失败—修复—验证—沉淀技能”闭环，让编码智能体不再每个任务都从零调试，而是把已经验证过的失败修复积累为可跨任务、跨环境甚至跨机器人本体复用的技能。

## 论文真正解决的问题

现有 Code-as-Policy 方法已经能让大模型调用感知、规划和控制 API 编写机器人程序，但它们仍有两个根本缺陷。

一是**失败不可诊断**。普通环境往往只告诉智能体任务成功或失败，却不说明问题发生在感知、目标定位、抓取候选、运动规划、碰撞约束还是长程任务协调。缺少细粒度证据时，智能体只能反复改 prompt、换参数或重跑，很难形成可证伪的故障假设。

二是**经验不复利**。某个任务里发现的抓取恢复、导航绕障或目标消歧方法，任务结束后通常不会进入长期记忆。于是智能体解决第一百个任务时，并没有比解决第一个任务更有经验。

ASPIRE 的核心主张是：机器人智能体要实现持续改进，关键不只是换一个更强的基础模型，而是提供一套能暴露因果证据、验证修复并保存成功经验的外部学习系统。

## 系统主线

```text
任务进入 Coordinator
  -> 为任务分配 Actor 编码智能体
  -> Actor 编写机器人程序
  -> Robot Execution Engine 执行程序并记录原语级多模态轨迹
  -> Actor 根据轨迹定位失败并修复程序
  -> 在调试配置上重新执行，验证修复是否成立
  -> Coordinator 审核并提炼可复用模式
  -> 写入共享 Skill Library
  -> Evolutionary Search 对困难任务探索不同程序候选
  -> 后续任务检索已有技能，减少重复调试
```

Coordinator 和 Actor 不共享完整聊天历史或原始 rollout。跨任务传播的是经过压缩和验证的技能，因此每个 Actor 的上下文仍聚焦于当前任务、当前程序和当前失败轨迹。

## 三个核心组件

### Robot Execution Engine：让失败变得可定位

执行引擎为每个感知、规划、抓取和控制原语记录：

- 调用的 API、输入参数、输出结果与返回状态；
- 调用前后的 RGB 关键帧，而不是整段视频；
- 分割覆盖层、物体位姿、抓取候选和运动规划结果；
- 与失败原语相邻的日志和视觉证据。

这种设计把“任务失败”拆成了可检查的局部因果链。论文中的收音机案例很典型：感知已经正确找到收音机，抓取也不是问题，真正失败的是导航目标落入桌子边缘的碰撞缓冲区，导致规划器持续返回 `PLANNING_ERROR`。智能体据此没有乱改感知 prompt，而是生成多角度接近策略，绕到物体另一侧后再执行抓取。

这个案例说明，ASPIRE 最重要的基础设施不是自动写代码本身，而是**给编码智能体提供足以完成故障归因的执行证据**。

### Skill Library：保存修复模式，而不是保存完整任务

技能库不会简单存储“如何拿起收音机”的整段程序，而是保存更容易迁移的修复知识，例如：

- 多实例物体的前后左右消歧；
- 针对不同物体的 SAM3 prompt；
- 低置信度定位结果过滤；
- 障碍边界附近的多角度接近；
- waypoint hopping 与探索式导航；
- 抓取约束、运动原语和调试工作流；
- 已知无效做法形成的负向约束。

每条技能包含失败特征、适用条件、修复策略以及必要时的代码草图。技能不是预先设计好的固定分类，而是从真实失败和已验证修复中归纳出来。Actor 提交结构化 findings，Coordinator 检查 API 合规性和复用价值，只有通过调试验证的模式才进入共享库。

这里最值得记住的是：**技能的 owner 是经过验证的失败—修复模式，而不是某个任务的最终程序。** 这使技能能跨任务迁移，也降低了把偶然成功当成通用经验的风险。

### Evolutionary Search：避免困在同一种修法里

单轨迹调试容易进入局部循环：智能体不断修补同一套程序，却没有尝试本质不同的解决策略。ASPIRE 因此对“机器人程序本身”做演化搜索。

每一轮由编码智能体根据技能库、历史最佳程序和剩余失败轨迹生成一组候选程序；执行引擎在相同调试种子上运行候选；下一轮保留表现较好的程序，并结合它们尚未解决的失败继续产生新候选。达到成功阈值或耗尽预算后，再在独立验证配置上检查最佳程序，并提炼可迁移模式。

演化搜索的作用不是替代执行引擎，而是在执行引擎已经能准确诊断的基础上扩大假设空间。论文消融也表明，执行引擎贡献最大，演化搜索主要补足剩余困难任务。

## 实验设置

仿真实验统一使用 Claude Code 搭配 Claude Opus 4.6 和 1M token 上下文窗口，在 CaP-X 中编写 Python 机器人程序。感知、几何和运动规划 API 在各实验中保持一致。

论文覆盖三类基准：

| 基准 | 关注能力 | 任务特点 |
|---|---|---|
| LIBERO-Pro | 扰动下的短时域鲁棒性 | 物体、目标和空间任务，分别测试位置扰动与指令改写 |
| Robosuite | 接触密集型操作 | 单臂、双臂、堆叠、擦拭、装配和交接 |
| BEHAVIOR-1K | 长时域家庭移动操作 | 导航并拾取易拉罐、导航并拾取收音机 |

主要基线包括 CaP-Agent0，以及 OpenVLA、π0、π0.5 等端到端 VLA 策略。

## 关键结果

### LIBERO-Pro：整体成功率从 18% 提升到 72%

| 方法 | Object Pos | Object Task | Goal Pos | Goal Task | Spatial Pos | Spatial Task | Overall |
|---|---:|---:|---:|---:|---:|---:|---:|
| π0.5 | 17% | 1% | 38% | 0% | 20% | 1% | 13% |
| CaP-Agent0 | 22% | 18% | 26% | 17% | 12% | 14% | 18% |
| **ASPIRE** | **98%** | **95%** | **81%** | **45%** | **51%** | **60%** | **72%** |

ASPIRE 的优势在指令改写条件下尤其明显。端到端 VLA 在部分位置扰动上尚有表现，但任务语义变化后几乎失效；ASPIRE 依靠程序结构、执行诊断和技能复用保持了更强的适应性。

### Robosuite：双臂交接从 20% 提升到 92%

ASPIRE 在 7 个任务上的平均成功率为 81%，CaP-Agent0 为 68%。最显著的差距来自 `two_arm_handover`，成功率由 20% 提升到 92%。不过并非所有任务都提升：双臂抬举为 71%，略低于基线的 74%；螺母装配也只有 9%，说明现有 API 和搜索仍难处理高精度接触任务。

### BEHAVIOR-1K：长时域任务明显优于基线和人工程序

| 任务 | Human Task | CaP-Agent0 Task | ASPIRE Task |
|---|---:|---:|---:|
| 拾取易拉罐 | 72% | 72% | **88%** |
| 拾取收音机 | 36% | 56% | **88%** |

收音机任务中，ASPIRE 的导航成功率达到 100%，最终任务成功率达到 88%。这类结果更能体现细粒度轨迹和恢复技能的价值，因为失败往往来自导航、碰撞和抓取之间的连续耦合，而不是单次视觉识别。

### 技能库越大，零样本迁移总体越强

在 LIBERO-90 上积累技能后，论文直接在未见过的 LIBERO-Pro Long 任务上生成一次程序，不进行额外调试、重试或任务专属技能更新。

| 技能来源任务数 | Pos | Task | Overall |
|---:|---:|---:|---:|
| 0 | 0.0% | 9.4% | 4.7% |
| 25 | 5.6% | 21.8% | 13.7% |
| 50 | 13.8% | 29.2% | 21.5% |
| 90 | **22.6%** | **38.3%** | **30.5%** |

CaP-Agent0 的整体成功率只有 3.8%，π0.5 为 5%。从宏平均看，技能库呈现清晰的经验复利；但逐任务结果并不总是单调增长，说明库中也会出现过时、过度具体或误导检索的条目。

### Sim-to-Real：迁移的是调试先验，不是仿真策略

真实机器人采用不同本体、感知和控制 API，因此论文不是把仿真程序直接部署到真机，而是把仿真中发现的技能作为上下文指导交给真机编码智能体。

| 真机任务 | 无技能成功率 | 有技能成功率 | 总 token 变化 |
|---|---:|---:|---:|
| 碗放到盘子上 | 20/20 | 20/20 | 8.65M → 5.11M |
| 抬起易拉罐 | 13/20 | 19/20 | 61.94M → 6.58M |
| 打开/推动抽屉 | 0/20 | 11/20 | 334.917M → 81.67M |

这部分的合理结论是：失败修复模式可以跨本体减少真实调试成本。它还不能证明通用的 Sim-to-Real 策略迁移，因为实验只有三个技能，真实机器人仍依赖自己的执行反馈完成适配。

## 消融实验给出的真实优先级

在 LIBERO-Pro 上，不使用执行引擎和演化搜索时，宏平均成功率约为 14%；加入 Robot Execution Engine 后达到 62%；再加入 Evolutionary Search 后达到 72%。

因此三部分并不是同等重要：

- **执行引擎是主要增益来源**，因为没有可观测、可归因的失败证据，后续反思和搜索都缺少可靠依据；
- **技能库负责跨任务复利**，零样本曲线证明经验积累确实有收益；
- **演化搜索负责困难任务的尾部提升**，但增加迭代后收益逐渐递减，计算成本较高。

## 我对这篇论文的判断

这篇论文最有价值的地方，不是“让 LLM 写机器人代码”这个表面现象，而是把机器人学习问题重新组织成一种接近软件工程智能体的持续调试系统。它把原本模糊的 rollout 失败变成原语级证据，把一次性的修复变成有准入条件的技能，把单路径自我反思扩展为多候选程序搜索。

论文也说明，Agent 的能力并不只属于模型本身。Claude Opus 4.6 固然很强，但真正使经验能够累积的是模型外部的 harness：结构化 trace、执行和验证边界、共享技能 owner、检索机制以及搜索预算。换句话说，**可学习的机器人系统不仅需要 policy，还需要一套管理证据和经验的运行时。**

我最认可的是技能表示方式。保存完整任务程序很容易过拟合场景和 API，而保存“失败特征—适用条件—修复策略—验证证据”更接近可迁移的工程知识。这也给 Agent memory 一个很明确的启发：长期记忆不应该只是对话摘要或成功轨迹，而应该优先保存已经被执行验证过的决策规则。

## 局限与风险

- 系统依赖 Claude Opus 4.6、1M 上下文和大量仿真 rollout，尚未证明较小模型也能维持同等质量的调试闭环。
- 机器人能力仍被预定义 API 限制。任务需要的新感知或控制原语不在接口内时，智能体无法真正突破能力边界。
- 真机仍缺少廉价可靠的成功检测、自动复位、安全监控和校准维护，因此还不是完整的现实世界终身学习系统。
- 技能库尚未解决长期治理问题，包括冗余、冲突、过期、错误检索和重新验证。逐任务零样本结果的非单调性已经暴露了这个风险。
- 演化搜索需要多轮 LLM 调用和环境执行，成本很高；对真实机器人而言，时间、磨损和安全风险会比仿真更突出。
- 论文的主系统使用非常强的 frontier model，而基线系统的外部支架能力并不完全等价，因此结果同时包含模型、可观测性和系统工程差异，不能简单理解成某个单一算法提升了 54 个百分点。

## 与我的研究和项目关联

这篇论文可以和我现有的三个方向直接连起来。

**与具身智能评估的关系。** [[Embodied-Reasoner - Synergizing Visual Search Reasoning and Action for Embodied Interactive Tasks]] 更关注 Observation-Thought-Action 轨迹、搜索效率和任务完成度；ASPIRE 则进一步要求评估系统能够指出失败发生在哪个机器人原语，并验证修复是否跨种子成立。后续做具身 Agent 评估时，不能只记录最终 success，还应记录 stage、失败签名、恢复动作、重试成本以及是否复用了历史技能。

**与 Agent Harness 的关系。** [[General Modular Harness for LLM Agents in Multi-Turn Gaming Environments]] 把 perception、memory、reasoning 做成可插拔模块；ASPIRE 展示了机器人领域更工程化的一版 harness：执行引擎负责可观测性，技能库负责长期记忆，演化搜索负责探索。两篇论文共同说明，Harness 不是 prompt 外壳，而是 Agent 的状态、证据、工具和验证协议。

**与 G1 / Dex3 和 π0.5 项目的关系。** 对 G1 灵巧手或双臂任务，最值得迁移的不是直接照搬 ASPIRE，而是先建立原语级 trace：目标检测结果、抓取候选、关节/末端轨迹、规划返回码、碰撞原因、夹爪宽度、力矩和最终状态。只有这些证据稳定存在，后续才有可能让编码智能体自动定位失败并沉淀技能。对于 π0.5 一类端到端 VLA，ASPIRE 也提示了一条互补路线：VLA 负责产生动作或高层意图，外部 harness 负责失败诊断、恢复程序和跨任务经验管理。

## 后续值得追的问题

- 技能库的检索、冲突消解、版本化和淘汰机制应该如何设计，才能避免规模扩大后的负迁移？
- 如何把每条技能的验证范围表示清楚，例如适用机器人、API 版本、对象类别、场景几何和随机种子覆盖？
- 对真机而言，什么样的成功检测和安全 reset 能让闭环真正无人化？
- 演化搜索能否用更便宜的 surrogate、离线日志或分层候选筛选减少真实 rollout？
- 如果把执行引擎和技能库保持不变，换成更小的开源模型，性能会下降多少？这能更清楚地区分模型能力和 harness 能力。
- 能否把 ASPIRE 的失败技能与 VLA 的训练数据闭环起来，让程序修复不仅指导下一次推理，也反向生成可训练的恢复轨迹？

## 我的最终收获

读完这篇论文后，我对“机器人 Agent 持续学习”的理解更具体了：持续学习不一定先从更新模型权重开始，也可以从持续积累经过验证的外部技能开始。真正形成复利的不是模型写过多少代码，而是系统是否保留了失败证据、修复条件和验证结果。

对我后续做具身系统最直接的启发是：**先把执行环境做成可诊断的，再谈自动反思；先把修复做成可验证的，再谈长期记忆；先定义技能的准入和失效条件，再谈技能库规模。** 如果 trace 不可靠、成功判定不闭合，Agent 写再多反思也只是猜测；如果技能没有适用边界和回归验证，经验积累反而可能变成错误累积。

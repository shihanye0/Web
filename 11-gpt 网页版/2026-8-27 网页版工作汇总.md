# 二、网页版最重要的成果：把“为什么不抓”真正拆清楚了

最开始现象很容易让人怀疑：

```text
模型是不是不会抓
数据是不是太少
脚本是不是在等某个条件
DIP是不是有问题
blend是不是有问题
```

现在已经收敛成两个真正的 P0 主问题。

### 主问题 1：缺少真正的 `SCENE_READY`

人工手动摆放药瓶是正常流程。

错误并不是“画面里出现了人手”，而是：

```text
PREPOSE完成
被错误地当成
场景准备完成
```

旧成功版本 PREPOSE 经常持续约 12 秒，这个时间无意间同时承担了：

```text
机器人到位
+
人工摆药瓶
+
人手退出
+
场景稳定
```

后来 PREPOSE gate 被合理优化后，最新运行约 1.2 秒就完成，随后马上进入 GRASP。

于是：

```text
人还在摆药瓶
↓
VLA已经拍第一帧
↓
模型看到移动/遮挡/尚未稳定的场景
↓
raw chunk预测 hover / approach
而不是 close
```

所以正确修复不是恢复：

```text
sleep 12 秒
```

而是建立真正的：

```text
PREPOSE
↓
SCENE_SETUP
↓
机器人 HOLD
↓
人工摆放
↓
人退出
↓
READY
↓
SCENE_READY
↓
第一次 policy observation
```

这是网页版分析得到的第一个核心根因。

# 三、第二个核心成果：找出了 short-horizon scheduler 的时间错误

当前失败版后来加入：

```python
GRASP_REFRESH_AT = 1
GRASP_EXEC_HORIZON = 12
```

并在 GRASP 阶段强制：

```text
j_off = 0
```

但实际模型 inference 大约：

```text
360–520 ms
```

机器人约：

```text
30 Hz
```

也就是说一次推理期间，机器人实际上已经前进：

```text
≈11–16 policy steps
```

于是当前失败链实际上是：

```text
t0:
拍图 + measured state
↓
模型针对 t0 生成 chunk

约400ms以后：
机器人已经往前走约12~15步
↓
新chunk返回
↓
却从 row0 开始执行
```

所以新 chunk 和机器人当前状态之间存在一个明确的时间错位。

这不是：

```text
抓取阈值不合适
```

也不是：

```text
timeout太短
```

而是：

> **异步 inference 的 observation 时间和 action activation 时间不在同一坐标系。**

# 四、网页版还重新解释了为什么旧版 nearest-row 能成功

冻结的 `5788bff` 没有现在的：

```text
refresh@1
12-step horizon
GRASP强制j_off=0
```

它使用的是较晚：

```text
refresh_at≈35
```

以及根据当前状态选择下一块中的一个 row。

旧成功日志里出现过：

```text
j_off:
20
15
17
7
16
17
...
```

以前我们只看到它的缺点：

```text
有时 nearest 会跳到 30+
```

但这次深入分析以后发现，它实际上还在做一件非常重要的事情：

> **隐式 inference-latency compensation。**

模型约慢 13 帧，新 chunk 返回时机器人也前进了大约十几帧，所以 nearest 经常自然落在十几行。

因此：

```text
global nearest
```

确实不够安全，

但：

```text
永远 row0
```

更错误。

最终设计变成：

```text
时间先确定大概在哪一行
↓
状态只在附近做微调
```

# 五、后来又把这个修复进一步升级成 policy-clock

这是 A2 最终审查时发现的一个很重要的深层问题。

最开始 A2 用：

```text
wall delay × 30Hz
```

来估算应该前进多少 action rows。

GRASP 正常播放时基本成立。

但 POUR 里代码本身会 slow-motion：

```text
真实时间过去 0.8s
≠
policy trajectory 前进 24 rows
```

可能实际上只走了约 12 rows。

如果继续用 wall-clock：

```text
0.8 × 30 = 24
```

就会导致抓取修好以后，倒药阶段重新产生错误 `j_off`。

所以 A2-FINAL 改成：

```text
request_policy_x
```

和：

```text
activation_policy_x
```

真正计算：

```text
policy_delay_steps
=
activation_policy_x
-
request_policy_x
```

例如：

```text
request @ row 35.4
activation @ row 47.5

policy_delay = 12.1
```

即使真实墙钟用了 800ms：

```text
wall_delay = 800ms
policy_delay = 12 rows
```

也可以同时正确。

这是目前 scheduler 最核心的最终设计：

> **action alignment 根据实际 policy progression，而不是根据现实墙钟猜。**

# 六、网页版还排除了几个“看起来很像根因、其实不是首发根因”的东西

这一点非常重要，因为避免继续乱改。

### `blend_off`

它确实可能造成顿挫：

```python
blend_off = cur - chunk[j_off]
...
blend_off *= 0.85
```

但严格对比以后发现：

> 5788bff 成功版本来就已经有 blend。

所以它不能解释：

```text
原来成功
→
现在失败
```

真正的问题是 short-horizon 让它从“偶尔触发”变成“每约 0.4 秒重新触发”。

因此：

```text
blend = 放大器
```

而不是：

```text
blend = 首发根因
```

所以 A2-FINAL 没有顺手重写它。

---

### DIP

旧成功链也存在 DIP。

所以：

```text
DIP=0.03
```

不能解释 Attempt1 为什么突然不抓。

它确实存在 retry 生命周期技术债，但不是第一根因。

---

### `cur` measured/commanded 混用

这是真正的架构问题。

当前 client 里：

```text
read_state24()
```

是真实 measured state。

服务器收到的 policy proprio 也是 measured state。

但之后：

```python
cur = apply_target(...)
```

又把 commanded target 继续叫 `cur`，随后 grasp/drop/gravity/blend 等地方会混用。

最终应该拆成：

```text
meas_state
cmd_state
```

但是冻结成功版也存在这个旧债。

所以：

> 值得后续重构，但不能拿它解释这次突然从成功变失败。

# 七、网页版也明确了 retry 为什么越试越怪

当前失败以后：

```python
tgt[10:] = 0.0
```

会重新改变 Dex3 手部状态。

但某些 partial thumb 又不真正收敛到 PREPOSE。

真实最新日志已经出现类似：

```text
R-Th0 residual

Attempt1 ≈ 0.17
Attempt2 ≈ 0.63
Attempt3 ≈ 0.59
```

所以 Attempt2/3 根本不是：

```text
完全相同实验再试一次
```

而是：

```text
从已经被reset改变的proprio状态重新开始
```

这就是为什么第一轮最终诊断版固定：

```text
max_attempts = 1
```

不是永久取消 retry。

而是先避免：

```text
retry bug
```

污染对主根因的验证。

# 八、网页版也重新定位了“数据不足”的优先级

目前**没有建议直接补数据或者重训**。

原因是旧成功链已经证明：

```text
同类模型
+
P425
+
相同任务体系
```

曾经自然产生过：

```text
finger≈1.02
↓
grasp confirmed
↓
POUR
```

并且 P425 stats 本身明确包含很强的 finger-close action。

所以现在更加合理的实验顺序是：

```text
先修 deployment execution contract
↓
再看 raw model 是否恢复 close
↓
如果仍不 close
再进入数据/模型诊断
```

而不是：

```text
机器人不抓
↓
立即重新采数据
```

# 九、网页版最终还加了一系列“防止以后出现幽灵问题”的 hardening

A2 最终审查不只看当前抓取问题，还检查了：

> 修复以后会不会又从旁边冒出一个新的问题？

因此最终设计还处理了这些风险：

```text
没有 camera frame
→ 不允许继续 inference
```

避免 server 沿用 dataset template image。

```text
alignment metadata 缺失
→ abort
```

而不是偷偷 fallback 到旧 nearest。

```text
policy delay 超出允许窗口
→ abort
```

而不是静默 clamp 到 row34。

```text
JOFF0 / ENVCAP 等父shell环境变量
→ 禁止偷偷改变实验行为
```

```text
Dex3 左右手没有真实收到 telemetry
→ 不允许继续
```

而不是把全零初值当真实 hand state。

```text
READY
→ 要求真正 interactive terminal
```

避免自动 stdin 意外越过人工场景确认。

这些不是为了“增强策略”，而是为了：

> **让错误尽早暴露，而不是以错误状态继续控制机器人。**
